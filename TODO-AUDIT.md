# TODO po audycie 2026-09-20

Audyt statyczny frontendu; bez połączeń i zapisów do Supabase. W repozytorium nie ma definicji RPC/RLS, więc poniższe ryzyka serwerowe wymagają osobnej weryfikacji.

- **Krytyczne — tożsamość i uprawnienia:** aplikacja odtwarza pracownika z sessionStorage i przekazuje jego ID jako `p_requester_id`; nie widać sesji Supabase Auth. Zweryfikować w RPC/RLS powiązanie żądania z uwierzytelnionym użytkownikiem, aktywność, aktualną rolę i lokal oraz właściciela rozpoczynanej/kończonej pozycji. Sam frontend nie może zapewnić autoryzacji. Zmiana roli/dezaktywacja pracownika nie odświeża zapisanej sesji.
- **Wysokie — kilka planów dnia:** `pobierzPlan` (employee) i `zmienDatePlanu` wybierają najnowszy plan przez `limit(1)`. Starsze aktywne plany nie są dostępne employee; zmiana daty może otworzyć inny plan niż oczekiwany. Potrzebny jawny wybór planu po ID, z nawigacją zależną od roli. ScheduledPlansScreen już otwiera konkretny ID.
- **Wysokie — zbiorcza edycja:** dodano blokadę wejścia dla własnych, powtórzonych i rozpoczętych/zakończonych pozycji. Pozostaje konflikt, gdy ktoś zmieni plan po otwarciu formularza. `update_production_plan` dostaje listę bez ID pozycji i bez wersji planu; zweryfikować atomowość i ochronę przed utratą postępu/równoległych zmian. Docelowa edycja powinna zachowywać ID i sprawdzać konflikt po stronie serwera.
- **Wysokie — Realtime:** subskrypcja obejmuje tylko Plan_items otwartego planu. Nie obserwuje zakończenia/usunięcia Plans, powstania nowego planu na ekranie „brak planu”, zmiany dnia o północy ani listy zaplanowanych. Zweryfikować także dostarczanie DELETE przy filtrowanej subskrypcji i konfigurację publikacji. Potrzebna spójna synchronizacja statusu planu i odświeżenie po reconnect; RPC muszą odrzucać operacje na nieaktywnym planie.
- **Wysokie — współbieżność:** uporządkowano odpowiedzi samych odczytów Realtime i odrzucono wyniki poprzedniego lokalu/planu/sesji. Nadal możliwy jest wyścig odczytu Realtime z odświeżeniem po mutacji w tym samym planie oraz nadpisanie zmian przez dwóch użytkowników. Sprawdzić transakcyjność start/complete/delete i reguły zakończenia planu przy niezakończonych pozycjach.
- **Ponowienia zapisów:** lokalne blokady chronią podwójne logowanie, zapis planu i dodanie pozycji. Nie zapewniają idempotencji po utracie odpowiedzi sieciowej ani między kartami. Wymaga to kontraktu RPC. Pozostałe mutacje również wymagają serwerowej ochrony przed powtórzeniem.
- **Nawigacja:** równoległe pobieranie historii/listy/pracowników w tym samym kontekście może zmienić ekran według kolejności odpowiedzi. Warto osobno ujednolicić anulowanie nawigacji; obecne zabezpieczenie obejmuje zmianę lokalu, planu, daty i wylogowanie.

# Інструкції адміністратора: працівники, доступи, структура

Дата: 2026-11-15. Спершу — підтримувані дії в застосунку. SQL нижче **лише читає** (Dashboard → SQL Editor,
роль `postgres`); у запитах замініть `0 /* номер працівника */` на справжній номер — без заміни запит
просто нічого не поверне. Номер працівника видно в `prod_employee_inventory.sql` (E3–E5) або в адресі
картки. Ніколи не публікуйте e-mail, PIN, паролі, токени чи ключ `service_role`.

Правила, на яких ґрунтуються кроки: `docs/employee-management-business-logic-uk.md`.

Загальна перевірка працівника (використовується в усіх розділах):

```sql
SELECT e.id, e.role, e.active, e.archived_at IS NOT NULL AS archived, e.location_id, e.department_id,
       e.production_role, e.position IS NOT NULL AS has_position, e.auth_user_id IS NOT NULL AS linked,
       u.email_confirmed_at IS NOT NULL AS email_confirmed, coalesce(u.encrypted_password, '') <> '' AS has_password,
       u.email LIKE '%@pin.%.invalid' AS pin_account, coalesce(u.banned_until > now(), false) AS banned,
       (SELECT manager_employee_id FROM app_private.org_assignments(current_date) a WHERE a.employee_id = e.id) AS current_manager
FROM public."Employees" e LEFT JOIN auth.users u ON u.id = e.auth_user_id
WHERE e.id = 0 /* номер працівника */;
```

---

## 1. Створити працівника

| | |
|---|---|
| Права | owner / administrator — будь-яка роль; manager — лише su-chef, shift-manager, sushi-master, crafter у своїй локації |
| Шлях A (рекомендовано для офісних ролей) | «Робота» → «Адмін панель» → «Працівники» → «Додати працівника» → Ім’я, Посада, Роль у системі, Локація / приміщення, «Активний працівник» → «Зберегти» |
| Шлях B (кухня, менеджер локації) | Zagotówki → «Pracownicy» → «Dodaj pracownika» → Imię, Rola, Lokal, Aktywny → «Zapisz» |
| Потрібно | ім’я; роль; локація для всіх ролей, крім owner / administrator / director / expert / specialist |
| Результат | рядок у `Employees`; входу ще **немає** (розділи 2–3) |
| Перевірка | загальний запит (`linked = false`) |
| Помилки | «Wybierz lokal»; «Nieaktywny lub nieistniejący lokal»; «Manager zarządza tylko…»; «Змінюйте відділ і підпорядкування у версії структури» — див. примітку |
| Безпека | не створюйте другий запис для людини, яка вже є (у тому числі архівна — її відновлюють, розділ 12) |

**Примітка (відомий дефект).** Якщо в «Структура» вже є версія структури, не заповнюйте «Відділ» і «Керівник»
при створенні — збереження завершиться помилкою й нічого не створить. Створіть без них, потім розділи 9–10.

## 2. Видати вхід e-mail (administrator, manager, director, expert, specialist)

| | |
|---|---|
| Права | owner або administrator |
| Шлях | картка в «Pracownicy» або рядок в «Адмін панель → Працівники» → «Запросити» → Email → «Надіслати запрошення» |
| Потрібно | активний працівник з e-mail-роллю без входу; e-mail, яким володіє саме ця людина («її власник отримає доступ як цей працівник») |
| Результат | лист від Supabase; стан «Запрошено»; `auth_user_id` записано |
| Перевірка | `SELECT status, result, created_at, finished_at FROM app_private.employee_invitations WHERE employee_id = 0 /* номер */ ORDER BY created_at DESC;` → `linked`, `OK` |
| Помилки | `AUTH_ACCOUNT_EXISTS` (адреса вже має акаунт — розділ 8); `INVITE_EMAIL_NOT_AUTHORIZED` (SMTP); `INVITE_RATE_LIMIT`; «Zaproszenie wysłano, ale konto wymaga ręcznego powiązania» — **не надсилати повторно**, розділ 8 |
| Безпека | одна активна резервація на працівника; не відправляйте повторно при стані «Перевірка запрошення — не надсилайте повторно» |

Owner не має кнопки запрошення в UI (немає такого шляху в коді).

## 3. Видати PIN (su-chef, shift-manager, sushi-master, crafter, employee)

| | |
|---|---|
| Права | owner або administrator |
| Шлях | «Pracownicy» → картка → «Nadaj / resetuj PIN» → новий PIN → зберегти |
| Потрібно | активний працівник з PIN-роллю |
| Результат | технічний Auth-акаунт `…@pin.<середовище>.invalid`, `auth_user_id` записано |
| Перевірка | загальний запит: `linked = true`, `pin_account = true` |
| Помилки | «Ten PIN jest już zajęty. Wybierz inny.»; «Pracownik ma konto innego typu…» (є e-mail-акаунт — розділ 8); «Nadanie PIN-u wymaga aktywnego konta» |
| Безпека | PIN передавати особисто; повторне «Nadaj / resetuj PIN» замінює старий |

## 4. Підтвердити запрошення (робить працівник)

Працівник відкриває лист → посилання веде на застосунок з `?auth=password` → задає пароль → входить.
Перевірка адміністратора: стан «Доступ активний»; загальний запит: `email_confirmed = true`, `has_password = true`.
Якщо посилання «не працює»: розділ 11.

## 5. Посада

Права: `tasks.admin` + `employees.manage` (owner, administrator). Шлях: «Адмін панель» → «Працівники» →
«Редагувати» → «Посада» → «Зберегти». До 160 символів, зайві пробіли прибираються. Права **не** змінює.
Перевірка: E8 у `prod_employee_inventory.sql`. Посада потрібна, щоб людину можна було призначити на крок
процесу «за посадою».

## 6. Роль у системі

Права: owner / administrator — будь-яка; manager — лише виробничі ролі своєї локації. Шлях: «Редагувати» →
«Роль у системі» (або «Rola» у «Pracownicy») → «Зберегти». Діє одразу після збереження (працівник побачить
інший набір модулів після наступної перевірки сесії, ≤ 60 с). Помилка «Nie można usunąć ostatniego aktywnego
administratora» — спершу інший активний адміністратор з входом. Не змінюйте роль, щоб «дати права на один
день» — для задач є області доступу (розділ 10).

## 7. Виробнича роль, відділ, локація

* **Виробнича роль:** «Адмін панель» → «Редагувати» → поле з’являється лише для відділу «Виробничий».
* **Відділ:** новому працівнику — у формі (якщо немає версій структури); наявному — «Структура» →
  «Змінити відділ» (діє одразу) або нова версія структури (з дати).
* **Локація:** «Локація / приміщення» (або «Lokal»); менеджер не може змінити локацію.
* Перевірка: E7 (немає проблем), E10–E12.

## 8. Зв’язати або перезв’язати акаунт входу (ручна операція адміністратора бази)

У застосунку **немає** кнопки «розв’язати». Випадки: `AUTH_ACCOUNT_EXISTS`, частковий збій запрошення, людина
має технічний PIN-акаунт, а потрібен e-mail (або навпаки).

1. Read-only діагностика: загальний запит + `prod_employee_inventory.sql` E5, E6, E14.
2. Переконатися в особі людини поза системою.
3. Підготувати **окремий** перевірений SQL (зразок — `supabase/upgrades/production/07_manager_test_accounts.sql`):
   зберегти старий UUID у журналі `app_private.employee_auth_events`, від’єднати, видалити застарілий
   `pin_accounts`; затвердити розробником; резервна копія; виконати.
4. Старий Auth-акаунт **не видаляти** — заблокувати через Auth Admin API (`ban_duration`).
5. Видати новий вхід (розділ 2 або 3).

Не прив’язуйте акаунт «за e-mail» вручну і не записуйте `auth_user_id` без журналу.

## 9. Підпорядкування (керівник)

| Ситуація | Шлях |
|---|---|
| Версій структури ще немає | новий працівник — поле «Керівник» у формі; наявний — «Адмін панель» → «Структура» → «Налаштування роботи та доступів» → «Підпорядкування» |
| Версії структури є | «Структура» → «Створити майбутню структуру» → «Редагувати зв’язки» (Відділ, Керівник) → «Запланувати» з датою |

Права: `organization.manage` (owner, administrator). Помилки: «Підпорядкування не може утворювати цикл»,
«Оберіть активного керівника», «Уже є запланована версія. Спочатку скасуйте її.», «Додайте до версії всіх
неархівних працівників.». Перевірка: E13 (сьогоднішній керівник), E7 «more than one current reporting line».

## 10. Додаткова область доступу до задач

«Адмін панель» → «Структура» → «Налаштування роботи та доступів» → «Доступ до співробітника або підлеглих» →
Кому надати, право, ціль. Скасування — у тому ж списку. Це замість зміни ролі, коли людині треба бачити чи
планувати задачі конкретних працівників / відділу / локації.

## 11. Активувати / деактивувати

* Owner / administrator: «Pracownicy» → «Dezaktywuj» (підтвердження) / «Aktywuj»; або «Активний працівник»
  в адмін-панелі.
* Manager: «Aktywny» у формі для своїх працівників.
* Ефект деактивації: вхід припиняється протягом ≤ 60 с (повідомлення «Brak dostępu…»), нові сповіщення не
  надходять, історія зберігається. Не можна деактивувати себе й останнього активного адміністратора.
* Перевірка: загальний запит `active`.

## 12. Архівувати («Usuń») і відновити («Przywróć»)

* Права: owner, administrator. «Pracownicy» → «Usuń» → «Usuń konto». Дані **не видаляються**.
* Відновлення: фільтр «Archiwalni» → «Przywróć» → працівник неактивний → «Aktywuj».
* Акаунт входу залишається пов’язаним; після відновлення й активації людина входить тим самим способом.
* Перевірка: E3.

## 13. Відновити доступ («Brak dostępu…»)

| Перевірка | Дія |
|---|---|
| E6: акаунт без працівника | людина увійшла не тим акаунтом або зв’язок втрачено — розділ 8 |
| `active = false` / `archived = true` | розділи 11–12 |
| немає локації для ролі | розділ 7 |
| `banned = true` | акаунт заблоковано свідомо — розділ 8 |
| e-mail-роль, `has_password = false` | запрошення не прийнято — новий лист через «Запросити» лише якщо стан «Немає доступу» |
| PIN-роль, PIN забуто | розділ 3 |
| посилання з листа веде на старий адрес | Supabase → Authentication → URL Configuration: Site URL `https://zagotowki.vercel.app`, Redirect `https://zagotowki.vercel.app/?auth=password`; секрет `INVITATION_APP_URL` / `APP_URL` функції `invite-employee` = `https://zagotowki.vercel.app/` |

## 14. Довідкові дані Production

Відділи, локації, посади, підпорядкування, категорії задач визначає керівництво компанії. **Не копіюйте** з UAT:
тестових працівників («UAT Su-chef B», «UAT Employee E», «UAT Unlinked» тощо), UUID Auth, номери працівників,
тестові посади чи структуру. Наявність потрібних значень показує `prod_reference_data_inventory.sql` D9 і
`prod_employee_inventory.sql` E17; бракуючі значення вводяться через застосунок за цими інструкціями.
